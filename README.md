# Menu Profit Simulator

**[Open the live dashboard →](https://vanshika1302.github.io/Menu-Profit-Simulator/)**
A one-page tool: change an ingredient cost or a price on a simulated bistro and see the effect on
contribution profit, the menu engineering matrix and a ranked list of experiments. (Source:
`dashboard/template.html`; the page is generated into the root `index.html` and also opens
straight from disk.)

A portfolio project in decision analytics: given a restaurant's menu, recipes, ingredient costs
and weekly sales, which items and operational changes improve profit without hurting customer
demand, and how sure can we be?

> **The data is synthetic and the demand truth is authored.** The restaurant, its sales and its
> "true" price sensitivities are generated by `etl/generate.py` from a fixed seed. Nothing here is
> a real restaurant's data. The validation section shows where the method works and where it
> fails on this synthetic data, not real-world accuracy.

## Business problem

Menu decisions are made on instinct and on margin reports. Two things make them hard:

1. A price change only pays off if customers do not walk away, and **price elasticity is an
   assumption**, not something a restaurant has measured. A +5% price rise on a dish can look
   obviously good or obviously bad depending on a number nobody knows.
2. The usual evidence (before/after sales around a past price change) is confounded by season,
   trend and noise.

So the project does three things. It computes what is certain (cost, margin, the menu
engineering class). It shows what depends on elasticity as a **range across a low, medium and
high band**, with the **break-even elasticity** that decides each price change. And it turns the
uncertainty into a **ranked backlog of experiments** with guardrail metrics and stop rules, which
is how the assumption would actually get measured.

## Data

Generated, not downloaded: a casual full-service American bistro with 30 items in 6 categories
(seven contain beef), about 45 ingredients, recipes, an ingredient-cost history, and 52 weeks of
sales (1,560 rows). Five small CSVs plus one validation-only file, all under 100 KB, in
`data/synthetic/`. `python etl/generate.py` rebuilds them byte for byte from seed 42.

| File | Content |
|---|---|
| `menu_items.csv` | item, category, launch price |
| `ingredients.csv`, `recipes.csv` | ingredient list and bill of materials (kept narrow and stable) |
| `ingredient_costs.csv` | unit cost history |
| `weekly_sales.csv` | units and average selling price per item per week |
| `ground_truth.csv` | **validation only**: authored true elasticities and substitution shares |

Sales include seasonality (summer drinks, winter comfort food), holiday dips, a few mid-year
price rises and two short promos. There are deliberately too few price changes to pin elasticity
down: the history gives a noisy hint, which is the point.

**Why authored truth.** Hiding a known truth in a separate file lets the project check itself:
does the elasticity band contain the true value, does the profit range cover the true change, can
a simulated experiment recover it. The truth is read by one module only (`sim/validation.py`);
tests confirm the simulator, the warehouse views and the dashboard give identical results with
that file deleted or replaced by garbage, and that no true value appears in `index.html`. The
truths themselves are authored from a thin evidence base, not empirical.

## Architecture

```
etl/generate.py  (seed 42)
        |  data/synthetic/*.csv   (+ ground_truth.csv, validation only)
        v
etl/load.py  -->  DuckDB warehouse  (raw_* tables; ground truth in a separate `validation` schema)
        |                 |
        |            sql/views.sql: item cost, contribution margin, 12-week baseline,
        |            popularity share, matrix inputs      sql/analysis_queries.sql
        v
sim/  pure Python reference model: model.py, matrix.py, scenarios.py, experiments.py
        |        (validation.py is the only reader of ground truth)
        |
        +--> notebooks/menu_profit_analysis.ipynb   (executed, no formulas of its own)
        +--> scripts/make_golden.py  -> tests/fixtures/golden.json  (35 scenarios)
                                          |
dashboard/sim.js  (JS port of sim/) <-----+  node tests/parity.mjs: 1e-9 on numbers, exact on classes and ranks
        |
scripts/export_dashboard.py + dashboard/template.html  -->  index.html  (GitHub Pages)
```

Python is the reference implementation. A small JavaScript port drives the sliders live, and a
parity test against golden scenarios keeps the two identical. The warehouse is DuckDB with plain
ANSI SQL, so moving to another engine is a connection change.

## How to run

```bash
pip install -r requirements.txt

python etl/run_pipeline.py            # generate the CSVs if missing, load DuckDB, create the views
python etl/run_queries.py             # business SQL: printed and saved as CSVs
python scripts/make_golden.py         # golden scenarios for the parity test
python scripts/export_dashboard.py    # writes the root index.html
pytest && node tests/parity.mjs       # tests, then JS-vs-Python parity (Node is dev-only)

python scripts/run_validation.py          # fast ground-truth scorecard -> validation_results.json
python scripts/run_validation.py --full   # adds the experiment-recovery Monte Carlo (about 20 s)
python scripts/build_notebook.py          # rebuild and execute the notebook
jupyter notebook notebooks/menu_profit_analysis.ipynb
```

Open `index.html` directly in a browser; it needs no server. CI (`.github/workflows/test.yml`)
runs the tests, the parity check, and confirms the committed `index.html` and golden fixtures
match a fresh build.

## Key findings

All figures are from the synthetic restaurant; weekly numbers are contribution profit (revenue
minus ingredient cost). Baseline: **$18,906 a week on $28,223 of sales, 33% food cost.**

**Margins and the matrix.** Chicken Parm is the largest single contributor ($1,812 a week). Per
category, the 30 items split 11 Stars, 8 Plowhorses, 6 Dogs and 5 Puzzles (whole-menu view:
8 / 8 / 7 / 7). Groups of four to seven items make the thresholds noisy, and the 70%-of-equal-share
rule is lenient, so the class split depends on how concentrated sales are.

**A cost shock is unambiguous.** Beef +20% hits the seven beef items and costs **$561 a week
(about $29,000 a year)**. With no price change there is no demand response, so the result does not
depend on elasticity and all three bands agree.

**A price change is not.** A +5% rise on Classic Burger has a break-even elasticity of **-1.62**:
it pays off only if demand is less elastic than that, and the assumed band (-0.5 to -1.8)
straddles it. Across 60 test price rises, **none** get a verdict of "pays off under all bands" or
"loses money under all bands": the break-even almost always sits inside a band this wide. The
headline is therefore a range, not a number. A +10% burger rise is worth between -$25 and +$142 a
week with no substitution, and +$179 to +$202 if every lost buyer switches to a similar dish, so
the substitution assumption matters too.

**Experiments, honestly priced.** Weekly item sales at this restaurant move around by about 17%
(median, seasonal drift included), and daily noise is assumed independent. On that basis no
single-item test fits in 12 weeks: a +5% burger test needs about 610 weeks, +10% about 154, +15%
about 69. Pooling helps a lot, because noise adds up more slowly than the effect: all seven
entrees at +10% need about 34 weeks and at +15% about 16, close to the 12-week cap. The dashboard
says so rather than hiding those tests: they go on a "Needs pooling or a larger effect" list,
and the "Feasible now" list is empty. Method-backed price tests rank ahead of the weak-evidence
portion and menu-design tests, whose stake is only an illustrative sizing. The takeaway is that
elasticity cannot be learned quickly from one item at one site: the options are a bigger effect,
pooled items, or longer tests.

## Validation

Scored against the authored truth (`sim/validation.py`). There are **no pass/fail bounds** on any
finding: bounds would invite tuning the bands or the generator until a number passes. Instead
the scorecard is saved to `validation_results.json`, and a test recomputes it and fails on any
change, so a result can only move on purpose. Misses are shown.

| Check | Result | What it says |
|---|---|---|
| True elasticity inside the assumed band | **87%** (26 of 30) | All four misses are drinks and sides, less elastic than the low band, by construction of the global bands |
| Profit range covers the true profit change | **72%** (60 scenarios) | Every miss is on the optimistic side: the truth is better than the range's upper end. Drinks and sides cover 0% |
| Medium-band headline has the right sign | **90%** | In 6 of 60 cases it says a rise pays off when it loses money |
| Decisive verdicts | **0 of 60** | A band this wide leaves the break-even inside it, so "pays off under all bands" never fires |
| Naive before/after estimate from price history | median error **0.87** | 9 historical price changes; two have the wrong sign (Classic Burger +0.42 against a truth of -0.73) |
| Switchback test recovers the right call, 12-week cap | **60%** | 200 simulated tests per entry: barely better than a coin flip, with a 90% interval about 8 elasticity units wide |
| Same test run for its powered duration | **83%** | The duration is years (about 290 to 610 weeks), so it is not achievable in practice |

This is the project's central claim in numbers: history alone gives a noisy, sometimes
wrong-signed answer, and a feasible test does not resolve it either, so the honest output is a
range plus a plan. All of this is on synthetic data with authored truth, so it shows the method
works and where it fails, not real-world accuracy.

## Limitations

- **Synthetic data and authored ground truth.** Nothing is empirical; the validation shows method behaviour, not real-world accuracy.
- **Elasticity is assumed.** The bands (-0.5, -1.0, -1.8) come from published ranges, item-level evidence is thin, and some research figures were not independently verified (see the research tickets under `.scratch/`).
- **The global bands miss about five items by design**, mostly drinks and sides, so some profit ranges do not cover the truth.
- **Price changes are meant to stay within about ±15%.** Demand is constant-elasticity.
- **Substitution is single-pass and within a category**, in proportion to popularity, with no other cross-price effects. Its share (default 25%) is an assumption.
- **No waste or yield modelling**, and the baseline (trailing 12 weeks, latest prices and costs) is not seasonally adjusted.
- **Matrix groups of four to seven items are noisy**, and the 70% popularity rule is lenient.
- **Total units stand in for traffic.** There are no covers, satisfaction, waste or staff-load measures.
- **Carryover (one block) and daily noise are assumed.** Noise is estimated from the synthetic data's week-to-week changes, with days assumed independent. Guardrail thresholds (units down 3%, profit down 2%) are policy choices, not evidence.
- **Menu-design and portion test evidence is weak**, and one widely cited label study has an integrity problem, so the backlog quotes no effect sizes for them. Their stake is an illustrative sizing, and their decision uncertainty is set to 1.0 because nothing supports a prior.
- **No sequential stopping boundaries are claimed.** Results are read at the planned end with a randomization test; always-valid inference is a possible upgrade.
- **Experiment results are not ingested back into the model.** A measured elasticity can be entered by hand per item in the dashboard.
- **Out of scope:** the LLM invoice/recipe-to-cost parser (the recipe and ingredient-cost schema is kept narrow for it), real datasets, multi-location restaurants and POS integration.
